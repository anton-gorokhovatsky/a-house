# Кабинет финала на GitHub Pages

GitHub Pages отдаёт интерфейс кабинета. Supabase проверяет логины, выдаёт каталог и PDF только аккаунтам из списка жюри. Вход выполняется напрямую через HTTPS API Supabase. Сеанс хранится в sessionStorage вкладки. При обновлении страницы кабинет проверяет доступ и открывает прежнюю работу. Кнопка «Выйти» завершает сеанс. Пароль не сохраняется.

## Настройка Supabase

1. Создайте отдельный проект для финала. Отключите свободную регистрацию и анонимный вход. Укажите URL кабинета в настройках Auth.
2. Выполните `schema.sql` в этом проекте. Политики допуска сравнивают идентификатор входящего пользователя со списком жюри. Каталог и PDF доступны только на чтение.
3. Запустите `provision.mjs` с двумя путями. Первый указывает на закрытую папку с ответами Supabase CLI `project.json` и `api-keys.json` для выделенного проекта `a-house-mts-jury`. Во втором лежит каталог, подготовленный `import-materials.py`.

```sh
node jury/final/hosted/provision.mjs /private/contest/setup /private/contest/final
```

Скрипт создаёт 15 индивидуальных учёток и закрытый бакет. После проверки допуска он сохраняет `public-config.json` для сборки и `jury-access.tsv` для организатора. Файлы с доступами и PDF хранятся в закрытых папках.

После входа над каталогом расположены приветствие, инструкция для роли пользователя и ссылка на регламент. Ссылка доступна сразу после входа. При нажатии PDF загружается из закрытого хранилища и открывается в новой вкладке. Для замены документа загрузите его в бакет `jury-final` по пути `regulations/d/<код папки>.pdf` или `regulations/i/<код файла>.pdf`, соответствующему ссылке в `jury_final_control.regulations_url`. Если PDF недоступен, ссылка ведёт к источнику организатора. Вкладка «Мой рейтинг работ» строится из сохранённых личных листов. Баллы отсортированы по убыванию, работы с одинаковым баллом делят место. В действующем листе технический эксперт видит рейтинг по своей оценке реализуемости. Организатор получает сводный результат отдельно.

В карточке листы расположены в горизонтальной ленте. Нажатие на лист открывает крупный просмотр со стрелками, счётчиком и масштабом. При закрытии фокус возвращается к выбранному в ленте листу. Просмотрщик PDF.js и его служебные файлы загружаются с домена кабинета, страницы читаются по частям из того же закрытого PDF в Supabase. Кнопка «Открыть PDF» открывает исходный файл целиком.

## Голосование в финале

После создания учёток примените по порядку `voting.sql`, `voting-50-50.sql`, `voting-role-split.sql` и `voting-nominations.sql`. Семь логинов `jury-01` – `jury-07` соответствуют строкам утверждённого состава в пункте 2.3. Номер 03 закреплён за Виктором Беловым, представителем технического блока МТС. Учётки 08–15 открывают материалы с правом просмотра.

На действующем листе в блоке 01 виден один критерий по шкале 0–5. Обычные члены жюри оценивают концепцию. Технический представитель МТС и его тестовый аккаунт оценивают реализуемость, эффективность и конструктивную логику с учётом технических требований. В итоговом расчёте каждая из двух частей имеет вес 50 %. В блоке 02 обе голосующие роли могут выбрать номинации. Член жюри может оставить комментарий и изменить свою оценку. Кабинет подтверждает сохранение после ответа сервера.

Рабочая сводка куратора доступна в SQL Editor по запросу `select * from public.jury_final_work_summary order by position`. Она учитывает только листы действующей редакции. Половину рабочего балла даёт средняя оценка концепции, половину — техническая оценка МТС. Рабочий балл появляется при наличии четырёх листов за работу и технической оценки. Призовой порог реализуемости из п. 7.4 проверяется отдельно. Для номинации архитектурного эксперимента реализуемость необязательна. Кворум всего этапа, сроки и решения проверяет куратор при оформлении протокола.

## Переключение и откат

Миграция сохраняет прежние критерии, бюллетени, комментарии и состояние приёма. Значение `original` в столбце `rubric` обозначает прежний лист, `final_50_50` — лист с двумя критериями. Укажите адрес документа с критериями в `jury_final_rubrics.criteria_url` для новой редакции, а ссылку на положение о жюри — в `jury_final_control.regulations_url`. Эти ссылки выдаются после входа. Когда новая сборка уже открывается по публичному адресу, переключите лист командой `update public.jury_final_control set active_rubric = 'final_50_50' where singleton`. Закрыть приём обеих редакций можно командой `update public.jury_final_control set accepting = false where singleton`.

Для возврата к прежнему листу выполните [rollback-50-50.sql](rollback-50-50.sql). Текущий клиент отобразит прежние критерии и восстановит сохранённые по ним ответы при следующем входе. Бюллетени 50/50 останутся в базе и вернутся при повторной активации. Открытая до переключения вкладка не сможет записать прежние ответы под новыми критериями.

Тег `jury-final-before-50-50-2026-11-26` закрепляет прежние исходники и файлы сайта в обоих репозиториях. При необходимости вернуть и прежнюю сборку сначала переключите базу, затем восстановите файлы из тега новым коммитом в ветке публикации. ## Комментарии для организатора

После настройки голосования выполните [organizer-comments.sql](organizer-comments.sql) в проекте Supabase. В Table Editor откройте схему `jury_admin` и представление `comments`. Каждая строка показывает работу, логин члена жюри, последний отправленный комментарий и время изменения. Тестовые записи помечены. Чтобы увидеть отзывы участников реального голосования, отфильтруйте «Тестовая запись» по значению `false`. Для просмотра нужен доступ организатора к панели проекта.

Член жюри видит свой отправленный текст в карточке работы после повторного входа. До нажатия кнопки сохранения черновик хранится в профиле браузера на устройстве автора. Удаление представления `jury_admin.comments` убирает список для организатора и сохраняет исходные бюллетени.

## Таблица результатов организатора

Лист «Сводка» показывает работы и рабочие баллы из `jury_final_work_summary`. В «Оценках жюри» видны все отправленные оценки финала, включая оценки без комментариев и помеченные тестовые записи. Имена членов жюри берутся из столбца «Член жюри» в закрытом списке `.work/jury-final-hosted/jury-final-access.tsv`, а имена тестовых пользователей — из их профилей. Исправление в кабинете заменяет оценку за ту же работу. Несохранённые черновики остаются у членов жюри.

Снимок для обоих листов читает `sheets-report.sql`. Расписание Codex на компьютере организатора запускает `sheets-delivery.js` с подключённым Google Диском. Оно сверяет идентификатор и тип таблицы, обновляет оба листа одним запросом и проверяет время снимка и количество строк на каждом листе. Доступом к таблице управляет организатор в Google Диске. В закрытом локальном каталоге `.work/jury-final-hosted/google-sheets` лежат `target.json` с идентификаторами файла и листов и исполняемый файл Supabase CLI. На время каждого обновления `sheets-lock.py` исключает одновременную запись. Остановить копирование можно в расписании Codex. Оригиналы голосов и комментариев хранятся в Supabase.

## Рекомендации по номинациям

После [разделения ролей](voting-role-split.sql) выполните [миграцию рекомендаций](voting-nominations.sql). Члены жюри обеих голосующих ролей могут отметить несколько номинаций и сохранить их вместе с оценкой. Организатор увидит названия в столбце «Рекомендации по номинациям» листа «Оценки жюри» после обновления отчёта.

## Сборка и проверка

Для сборки нужны Node.js 24 с npm, Git и tar. Возьмите созданный при настройке кабинета `public-config.json` с URL проекта и публичным ключом `sb_publishable_…`. Укажите новый каталог для результата.

```sh
node jury/final/hosted/release.mjs /private/contest/setup/public-config.json /tmp/a-house-jury-site
```

Команда берёт файлы из текущего коммита Git, устанавливает зафиксированные зависимости и браузеры и запускает обе проверки на тестовых данных. Первая проходит от входа до PDF и обратно. Вторая проверяет расчёт, сохранение, обе роли, номинации и адаптивную вёрстку. Браузеры по умолчанию — WebKit в профиле iPhone 13 и Chromium. Чтобы использовать установленный Google Chrome, запустите ту же команду с `JURY_CHROMIUM_CHANNEL=chrome`.

Для выпуска запустите команду из актуального коммита ветки `codex/jury-final` с флагом `--publish` и авторизованным GitHub CLI. Она публикует проверенную сборку в ветке `main` репозитория GitHub Pages, сохраняет `CNAME`, записывает полный SHA исходников в строку `Source-Commit` коммита и в файл `source-commit.txt` и проверяет отдачу файлов с рабочего домена. Корень сайта ведёт в `/jury/` и сохраняет ссылку на работу, если она была в адресе.

Для отдельной проверки опубликованного кабинета используйте тестовый доступ и уже установленные зависимости из `npm ci --prefix jury/final/hosted --omit=optional --ignore-scripts`.

```sh
node jury/final/hosted/check.mjs https://YOUR_PAGES_URL/jury/ /private/contest/setup /private/contest/final
```
